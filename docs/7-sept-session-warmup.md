# Исправление задержки первого ответа Web/TUI

В `6-sept` каждый новый пользовательский сеанс создавал отдельный клиент
модели. Для LiteRT это означало повторный prefill системного промпта в момент
первого сообщения. Прогрев исходного клиента CORE этому новому клиенту
не помогал. При отключении клиента подготовленная сессия уничтожалась.

Теперь планировщик готовит одну пользовательскую сессию до сообщения
`CORE socket ready`. После отключения Web/TUI она возвращается к сохранённой
основе системного промпта и остаётся готовой для следующего подключения.
История, режим чата и временное состояние команд очищаются. При ошибке
сброса сессия закрывается и повторно не используется. Возврат в резерв
происходит только после завершения/отмены всех запросов старого подключения.

Для LiteRT запуск CORE станет дольше на один прогрев пользовательской сессии;
его стоимость убрана из обычного первого запроса. Между подключениями
сохраняется память одной подготовленной сессии. Голос и уведомления сохраняют
свои отдельные контексты. Если новое подключение начинает работу до окончания
отмены старого запроса, может понадобиться новая сессия с прогревом.
Для удалённых API скорость серверного кеша определяется самим сервером.

Проверка на Radxa: обновить код и перезапустить CORE; дождаться
`CORE human session base ready` и `CORE socket ready`, открыть TUI, отправить
короткий вопрос, отключиться, затем повторить в Web. После обычного повторного
подключения в логе не должен появляться новый `litert-session-warm manager`.
Для проверки изоляции включить «Чат», передать произвольную тестовую фразу,
отключиться и убедиться, что следующее подключение начинается с чистого чата.

Локальные регрессионные проверки покрывают повторное использование без нового
fork, очистку истории и состояния, отказ от повторного использования при
ошибке сброса KV и ожидание окончания старых запросов. Реальное время первого
ответа и работу LiteRT необходимо проверить на устройстве.
