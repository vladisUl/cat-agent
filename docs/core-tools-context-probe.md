# Проверка нескольких Conversation на одном LiteRT Engine

Это самостоятельная **регрессионная проверка изоляции KV** двух живых
Conversation на одном LiteRT Engine. Одинаковые значения `token_count`
сами по себе не доказывают независимость хранимого состояния.

## Как устроен эксперимент

- Создаётся один `litert_lm.Engine` (CPU, настройки как в текущем CORE).
- `NativeConversationChat` прогревает BASE через `warm → OK`.
- Из BASE существуют **два живых клона** A и B, каждый со своей историей.
- Каждый получает своё случайное секретное слово из закрытого списка.
- Запросы отправляются **последовательно**: A1, B1, A2, B2.
- После каждого запроса снимается `token_count` обоих рабочих контекстов
  и исходного BASE, проверяется отсутствие изменений чужого KV.
- Модель отдельно спрашивается о слове **своего** диалога.

Запуск не выполняет shell, не создаёт файлы и не подключает Task SYSTEM.
По умолчанию в модель всё ещё передаются четыре описания MQTT-инструментов,
как у обычного менеджера; можно убрать их флагом `--disable-mqtt`.

## Запуск на WSL

На машине с ограниченной RAM **остановить тестовый CORE этапа 2**
(не завершать его во время активного вызова модели), чтобы этот скрипт
загрузил единственный Engine.

```bash
cd /opt/cat-agent
git pull --ff-only

PYTHONPATH=/opt/cat-agent/src /opt/litert-lm-venv/bin/python3 \
  -m unittest discover -s tests \
  -p 'test_litert_agent_tools*.py' -v

PYTHONPATH=/opt/cat-agent/src /opt/litert-lm-venv/bin/python3 \
  -m orchestration_tools.probe_contexts \
  --model /storage/models/litert/gemma-4-E4B-it.litertlm \
  --system-file /opt/cat-agent/prompts_tools/manager.md
```

Не нужно задавать `--enable-shell`: в этом пробнике он намеренно
отключён. Для диагностики LiteRT можно добавить `--trace-native-json`.

## Интерпретация

```text
BASE=..., A clone=..., B clone=...
A1: KV ... -> ...
KV after A1: A=... B=<BASE> BASE=<BASE>
B1: KV ... -> ...
KV after B1: A=<A1> B=... BASE=<BASE>
A2: ...
B2: ...
RESULT native KV isolation: PASS
RESULT model recalls own code: PASS
```

Ожидаемый результат: оба клона начинают с BASE; после каждого сообщения
KV меняется только у адресованного Conversation, BASE остаётся неизменным.
Модель A вспоминает своё слово и модель B — своё.

**Коды завершения:**

- `0`: прошли и KV-проверка, и воспроизведение секретных слов.
- `2`: обнаружено несоответствие KV-счётчиков — исследовать до
  перехода к пулу.
- `3`: счётчики не обнаружили вмешательства, но модель ответила
  неправильно или не в требуемом формате. Это **не доказательство**
  утечки состояния: возможна ошибка генерации.
- `1`: сбой инициализации или работы модели (в том числе памяти/контекста).

Это проверка **последовательного** переключения контекстов, а не
потокобезопасности LiteRT. Одновременную генерацию на одном Engine
по-прежнему не разрешаем.

Новые методы `NativeConversationChat.fork_dialogue()`,
`working_kv_tokens` и `base_resident_kv_tokens` предназначены для
дальнейшей поддержки пула; ответственность за закрытие возвращённого
клона лежит на вызывающем коде.
