# Общий Task SYSTEM

Task SYSTEM — отдельный процесс без модели. Он единственный владеет реестром
TASK, таймерами, MQTT-привязками и очередью запусков. LiteRT, OpenAI и llama.cpp
CORE используют удалённые клиенты, без собственных копий TaskStore и таймеров.
Исполнителями сохранённых TASK могут быть `litert` и `openai`; llama.cpp имеет
доступ к управлению. Разовые команды с периодом `0` остаются частью текущего
диалога и не создают сохранённый TASK.

## Первое обновление

1. Остановить **все старые CORE** перед первым запуском Task SYSTEM: старый код
   ещё пишет прежние файлы и самостоятельно запускает таймеры/MQTT.
2. Обновить репозиторий и выполнить тесты:

   ```sh
   cd /opt/cat-agent
   git pull --ff-only
   PYTHONPATH=/opt/cat-agent/src /opt/litert-lm-venv/bin/python3 \
     -m unittest discover -s tests -v
   ```

3. В отдельном терминале запустить один сервис:

   ```sh
   cd /opt/cat-agent
   ./start_task_system.sh
   ```

   Дождаться `TASK_SYSTEM_READY: /run/cat-agent/tasks.sock`.
4. Запустить CORE прежними командами и интерфейсы с выбором `litert|openai`.
   Task SYSTEM должен оставаться работающим независимо от CORE.

При первом запуске сервис импортирует `/var/lib/cat-agent/task.txt` и
`/var/lib/cat-agent/events.json` в `/var/lib/cat-agent/task-system.sqlite3`.
Старые файлы сохраняются, но больше не используются как рабочее хранилище.
У прежних заданий `executor=litert`. Повторный запуск сервиса читает SQLite,
а не импортирует прежние файлы заново. Редактировать старые файлы для
изменения действующих заданий больше нельзя.

## Исполнитель и управление

Каждый TASK содержит `executor=litert|openai`, по умолчанию `litert`, независимо
от CORE, через который задание создано. Управление из любого CORE одинаково.

Без участия модели доступны команды:

```sh
./task_system.sh list
./task_system.sh runs
./task_system.sh stop 1
./task_system.sh start 1
./task_system.sh period 1 120
./task_system.sh executor 1 openai
./task_system.sh delete 1
```

Создать периодическое задание с указанным исполнителем:

```sh
./task_system.sh create --executor openai --period 60 --skill shell \
  --description 'Проверка файла' \
  --text 'Проверить наличие user.txt и сообщить результат'
```

`./task_system.sh run 1` ставит один дополнительный запуск включённого задания
в очередь. Он также выполняется только назначенным CORE.

В обработчике команд модели поддержаны прежний синтаксис и необязательный
параметр исполнителя перед разделителем `--`:

```text
/work#task_timer.sh 60 shell --executor openai -- "Проверить наличие user.txt"
/work#timer.sh executor openai 1
```

Синтаксис `timer.sh period` прежний: сначала период, затем номер задания.
У административного `task_system.sh period` сначала номер, затем период,
как показано выше. Файлы промптов не изменены.

## Очередь и остановка

- `pending`: запуск ожидает назначенный CORE. На другую модель он не передаётся.
- `offered`: запуск выдан конкретному процессу CORE, но выполнение ещё не начато.
- `running`: CORE подтвердил начало; повторная выдача другому процессу запрещена.
- `done`, `error`, `cancelled`, `interrupted`: завершение или прекращение запуска.

Для одного номера TASK одновременно допускается только один выданный/работающий
запуск, даже при нескольких процессах одного backend. Повторная доставка ответа
и потерянное подтверждение завершения не создают нового запуска. Периодические
тики объединяются: пока запуск ожидает или выполняется, новые тики того же
поколения TASK не накапливаются. MQTT-события сохраняются отдельными запусками
с собственным значением и выполняются последовательно для одного TASK.

STOP/DELETE/смена периода или исполнителя меняют поколение TASK. CORE проверяет
его перед очередным шагом, освобождает агента при отмене, и только затем сервис
может выдать следующий запуск. Уже выполняющийся вызов модели или команда
завершается до этой границы. Удалённый и заново созданный TASK с тем же номером
не наследует старые запуски.

Если CORE недоступен до начала работы, запуск остаётся в очереди. Если CORE
аварийно завершился **после подтверждённого начала**, состояние `interrupted`
означает, что результат неизвестен. Этот конкретный запуск автоматически не
переигрывается: внешние команды могли уже выполниться. Следующие плановые
срабатывания продолжаются по расписанию. Журнал хранит последние 100 завершённых
запусков и все незавершённые; очередь ограничена 1024 запусками.

При перезапуске Task SYSTEM сохраняются задания, сроки таймеров, очередь и
выданные запуски. CORE ожидает восстановления связи на границе шага и продолжает
с прежним номером запуска. Идентичность процесса проверяется по PID, времени
его запуска и идентификатору загрузки Linux — повторное использование PID
не считается возвращением старого исполнителя.

## Проверка на Radxa

1. Создать TASK через OpenAI CORE, проверить его наличие через LiteRT CORE.
2. Выполнить STOP, смену периода и START через другой CORE; проверить общий список.
3. Назначить `openai`, остановить OpenAI CORE, дождаться срока TASK.
   В `./task_system.sh runs` должен остаться `pending`; LiteRT его не выполняет.
4. Запустить OpenAI CORE: ожидающий запуск должен перейти в `running`, затем
   завершиться один раз. В логе Task SYSTEM видны номер TASK, `run` и исполнитель.
5. Проверить удаление TASK через другой CORE и отсутствие последующих запусков.

Для отладки `CAT_AGENT_TASK_SOCKET` задаёт адрес **общего сервиса** и должен
совпадать у сервиса, CORE и административного клиента. `CAT_AGENT_TASK_DB`
выбирает базу сервиса. `CAT_AGENT_CORE_SOCKET` по-прежнему выбирает только
сокет связи интерфейса с CORE и не влияет на Task SYSTEM.
