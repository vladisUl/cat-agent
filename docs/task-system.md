# Общий Task SYSTEM

Task SYSTEM — отдельный процесс без модели. Он единственный владеет реестром
TASK, таймерами, MQTT-привязками и очередью запусков. LiteRT, OpenAI и llama.cpp
CORE используют удалённые клиенты, без собственных копий TaskStore и таймеров.
Исполнителями сохранённых TASK могут быть `litert` и `openai`; llama.cpp имеет
доступ к управлению. Разовые команды с периодом `0` остаются частью текущего
диалога и не создают сохранённый TASK.

## Первое обновление

1. Остановить **все старые CORE** перед первым запуском Task SYSTEM: старый код
   ещё пишет прежние файлы и самостоятельно запускает таймеры/MQTT.
2. Обновить репозиторий и выполнить тесты:

   ```sh
   cd /opt/cat-agent
   git pull --ff-only
   PYTHONPATH=/opt/cat-agent/src /opt/litert-lm-venv/bin/python3 \
     -m unittest discover -s tests -v
   ```

3. В отдельном терминале запустить один сервис:

   ```sh
   cd /opt/cat-agent
   ./start_task_system.sh
   ```

   Дождаться `TASK_SYSTEM_READY: /run/cat-agent/tasks.sock`.
4. Запустить CORE прежними командами и интерфейсы с выбором `litert|openai`.
   Task SYSTEM должен оставаться работающим независимо от CORE.

При первом запуске сервис импортирует `/var/lib/cat-agent/task.txt` и
`/var/lib/cat-agent/events.json` в `/var/lib/cat-agent/task-system.sqlite3`.
Старые файлы сохраняются, но больше не используются как рабочее хранилище.
У прежних заданий `executor=litert`. Повторный запуск сервиса читает SQLite,
а не импортирует прежние файлы заново. Редактировать старые файлы для
изменения действующих заданий больше нельзя.

## Исполнитель и управление

Новые TASK содержат `executor=auto` по умолчанию, независимо от CORE, через
который задание создано. При каждой выдаче RUN Task SYSTEM выбирает READY
OpenAI, иначе READY LiteRT; если оба NOT_READY, RUN остаётся pending.
Выбор записывается в RUN, а TASK остаётся `auto`.

Явные `executor=litert` и `executor=openai` — административное закрепление.
Прежние TASK не переводятся в auto. Управление из любого CORE одинаково.

Без участия модели доступны команды:

```sh
./task_system.sh list
./task_system.sh cores
./task_system.sh runs
./task_system.sh stop 1
./task_system.sh start 1
./task_system.sh period 1 120
./task_system.sh executor 1 openai
./task_system.sh executor 1 auto
./task_system.sh delete 1
```

Создать периодическое задание с указанным исполнителем:

```sh
./task_system.sh create --executor openai --period 60 --skill shell \
  --description 'Проверка файла' \
  --text 'Проверить наличие user.txt и сообщить результат'
```

`./task_system.sh run 1` ставит один дополнительный запуск включённого задания
в очередь. Для него действует та же политика TASK: auto либо явное закрепление.

В обработчике команд модели поддержаны прежний синтаксис и необязательный
параметр исполнителя перед разделителем `--`:

```text
/work#task_timer.sh 60 shell --executor openai -- "Проверить наличие user.txt"
/work#timer.sh executor openai 1
```

Синтаксис `timer.sh period` прежний: сначала период, затем номер задания.
У административного `task_system.sh period` сначала номер, затем период,
как показано выше. Файлы промптов не изменены.

## Очередь и остановка

- `pending`: запуск ожидает READY CORE для auto либо назначенный CORE для явного закрепления.
- `offered`: запуск выдан конкретному процессу CORE, но выполнение ещё не начато.
- `running`: CORE подтвердил начало; повторная выдача другому процессу запрещена.
- `done`, `error`, `cancelled`, `interrupted`: завершение или прекращение запуска.

Для одного номера TASK одновременно допускается только один выданный/работающий
запуск, даже при нескольких процессах одного backend. Повторная доставка ответа
и потерянное подтверждение завершения не создают нового запуска. Периодические
тики объединяются: пока запуск ожидает или выполняется, новые тики того же
поколения TASK не накапливаются. MQTT-события сохраняются отдельными запусками
с собственным значением и выполняются последовательно для одного TASK.

STOP/DELETE/смена периода или исполнителя меняют поколение TASK. CORE проверяет
его перед очередным шагом, освобождает агента при отмене, и только затем сервис
может выдать следующий запуск. Уже выполняющийся вызов модели или команда
завершается до этой границы. Удалённый и заново созданный TASK с тем же номером
не наследует старые запуски.

Если CORE недоступен до начала работы, запуск остаётся в очереди. Для auto
проверка готовности и выбор повторяются при выдаче. При потере CORE или lease
на стадии offer запуск возвращается в pending; следующая выдача получает новый
`offer_id`. Сообщения begin/finish от старого offer больше не действуют.
Начатый RUN не переносится на другой CORE даже при истечении heartbeat. Если CORE
аварийно завершился **после подтверждённого начала**, состояние `interrupted`
означает, что результат неизвестен. Этот конкретный запуск автоматически не
переигрывается: внешние команды могли уже выполниться. Следующие плановые
срабатывания продолжаются по расписанию. Журнал хранит последние 100 завершённых
запусков и все незавершённые; очередь ограничена 1024 запусками.

При перезапуске Task SYSTEM сохраняются задания, сроки таймеров, очередь и
выданные запуски. CORE ожидает восстановления связи на границе шага и продолжает
начатый RUN с прежним номером запуска. Не начатый offer может быть отозван. Идентичность процесса проверяется по PID, времени
его запуска и идентификатору загрузки Linux — повторное использование PID
не считается возвращением старого исполнителя.

## Проверка на Radxa

1. Создать TASK через OpenAI CORE, проверить его наличие через LiteRT CORE.
2. Выполнить STOP, смену периода и START через другой CORE; проверить общий список.
3. Назначить `openai`, остановить OpenAI CORE, дождаться срока TASK.
   В `./task_system.sh runs` должен остаться `pending`; LiteRT его не выполняет.
4. Запустить OpenAI CORE: ожидающий запуск должен перейти в `running`, затем
   завершиться один раз. В логе Task SYSTEM видны номер TASK, `run` и исполнитель.
5. Проверить удаление TASK через другой CORE и отсутствие последующих запусков.

Для отладки `CAT_AGENT_TASK_SOCKET` задаёт адрес **общего сервиса** и должен
совпадать у сервиса, CORE и административного клиента. `CAT_AGENT_TASK_DB`
выбирает базу сервиса. `CAT_AGENT_CORE_SOCKET` по-прежнему выбирает только
сокет связи интерфейса с CORE и не влияет на Task SYSTEM.


## Готовность CORE и Ollama

Heartbeat отправляется отдельным потоком каждые 5 секунд; lease истекает через
20 секунд без обновления. Поток запускается после успешной инициализации runtime
и запуска scheduler CORE. Диалоговые session contexts создаются лениво при первом
обращении и не являются условием старта heartbeat. Он продолжает работать во время
вызова модели. При остановке CORE снимает готовность; смерть процесса также учитывается.
Task SYSTEM не восстанавливает READY из SQLite после своего перезапуска —
нужно новое подтверждение работающего CORE.

LiteRT READY означает, что загрузка модели и инициализация runtime завершены.
Для OpenAI дополнительно каждые 30 секунд проверяются:

1. Локальный Ollama: GET `/api/tags` на сервере из `CAT_AGENT_API_BASE_URL`
   (например, `http://localhost:11434/v1` → `http://localhost:11434/api/tags`).
   Это запрос метаданных, а не генерация: [Ollama API](https://docs.ollama.com/api/tags).
2. Облачная квота: GET `https://ollama.com/api/usage` с Bearer-ключом из
   **environment процесса OpenAI CORE**, переменная `OLLAMA_API_KEY`.

Адаптер недокументированного usage endpoint изолирован в `ollama_usage.py`.
Текущая схема — `limits.monthly.usage`: число меньше 1 означает доступную квоту,
от 1 включительно — `quota_exhausted`. Ответы 401/403 дают `credentials_invalid`.
Ошибка сети/API, некорректный JSON или новая неизвестная схема дают NOT_READY.
Пропущенное поле, строка вместо числа, отрицательное значение и NaN не считаются
подтверждением доступной квоты. При отсутствии ключа причина — `missing_api_key`.

В Task SYSTEM передаются только признак готовности и фиксированный код причины.
Ключ не сохраняется в TASK, RUN или SQLite, не передаётся Task SYSTEM и не
логируется. Ответы и тексты исключений usage API тоже не логируются. HTTP-редиректы
этого запроса запрещены, чтобы не переслать ключ другому адресу.

READY — результат последней периодической проверки, а не гарантия следующего
запроса модели. Проверка подтверждает доступность локального API и квоту аккаунта,
указанного ключом; она не делает пробную генерацию. При сетевом сбое переключение
происходит после очередной проверки; при исчезновении heartbeat — по lease.

Проверка облачной готовности относится к auto. Явный `executor=openai` сохраняет
прежнюю семантику, в том числе без `OLLAMA_API_KEY`; запрос выполняется назначенным
CORE и может завершиться обычной ошибкой API. Пользовательские Web/TUI/Voice не
регистрируют готовность и не изменяют политику TASK.

Диагностика:

```sh
./task_system.sh cores
./task_system.sh runs
```

Пример состояния:

```text
openai NOT_READY quota_exhausted
litert READY
```

В JSON RUN поля `policy` и `executor` показывают политику и фактический выбор:
`"policy": "auto", "executor": "openai"`. Пока auto-RUN ожидает выбора,
`executor` равен null. Старые записи журнала могут не иметь `policy` — их прежнее
поле `executor` по-прежнему означает жёсткое закрепление.

## Обновление политики auto и ручная проверка

Остановить оба CORE и Task SYSTEM, обновить код и выполнить полный набор тестов
командами выше. Базу удалять не нужно. Затем запустить Task SYSTEM, оба CORE и
любые интерфейсы. Для облачной проверки ключ должен быть экспортирован в
окружение запуска OpenAI CORE; Task SYSTEM он не нужен. При интерактивном запуске
можно ввести ключ без отображения и без включения значения в историю команд:

```sh
read -rsp 'OLLAMA_API_KEY: ' OLLAMA_API_KEY
printf '\n'
export OLLAMA_API_KEY
./start_openai_agent.sh
```

Если существующий `.env.openai` задаёт ту же переменную, launcher применит значение
из него. Код проверки самостоятельно файлов с ключами не читает.

После прогрева проверить `./task_system.sh cores`. Новый TASK без `--executor`
получает auto. Для безопасной проверки создать задание только на чтение:

```sh
./task_system.sh create --period 3600 --skill shell \
  --description 'Проверка auto' --text 'Выполни pwd и верни текущий каталог'
```

Далее использовать номер, выданный при создании (ниже пример для TASK 1):

```sh
./task_system.sh run 1
./task_system.sh runs
```

1. При обоих READY фактический executor RUN должен быть openai, даже если
   диалог открыт через `./start_tui.sh litert`.
2. Дождаться завершения RUN, остановить OpenAI CORE, проверить `cores` и
   поставить следующий RUN — его должен взять litert.
3. Восстановить OpenAI CORE и дождаться READY. Следующий RUN должен выбрать
   openai; уже начатый RUN на litert не переносится.
4. Остановить оба CORE и поставить RUN — он останется pending. Запустить LiteRT:
   до окончания инициализации RUN ждёт, затем выполняется автоматически.
5. Для проверки закрепления выполнить `./task_system.sh executor 1 openai`:
   при отключённом OpenAI LiteRT этот TASK не берёт. Вернуть автоматический
   режим командой `./task_system.sh executor 1 auto`.
6. Удалить тестовое задание: `./task_system.sh delete 1`.

Исчерпание квоты, ошибки API, истечение lease и потеря offer проверяются
автоматическими тестами с управляемым временем и ответами HTTP; реальную квоту
для этого расходовать не нужно.
