# LiteRT server с сохранением контекста

Отдельный OpenAI-совместимый сервер **текста и изображений** для LiteRT-LM **0.16.0 / 0.16.1 / 0.18.0**.
Работает на Windows и Linux, не импортирует код cat-agent и не меняет его конфигурацию.
Зависимости: Python 3.10+ и уже установленный `litert-lm` поддерживаемой версии;
FastAPI, uvicorn и установка самого cat-agent не нужны.

## Что сохраняется

Модель загружается один раз при старте. Для каждого сочетания системного промпта
и параметров генерации сервер держит Session и checkpoint **после обработки базы**.
Клиент по-прежнему посылает полную историю в `messages`.

| Лог `mode` | Что произошло | Что обрабатывается заново |
| --- | --- | --- |
| `cold` | Новый системный промпт/настройки, либо слот был вытеснен | База и переданная история |
| `resume` | История точно совпала с сохранённой, добавлена реплика user | Только новая реплика |
| `base` | Новый независимый запрос с прежним системным промптом | Новая реплика, после возврата к checkpoint базы |
| `replay` | История изменена, сокращена или пришла из другого диалога | Переданная история после сохранённой базы |

Это покрывает поведение менеджера cat-agent: вне режима чата он сбрасывает историю
после ответа. Второй независимый запрос с тем же системным промптом использует `base`.
Предыдущий ответ и прошлые пользовательские сообщения при этом **не сохраняются
в видимом модели контексте**. Это кэш вычислений, не кэш готовых ответов.

По умолчанию два слота (`--max-contexts 2`), например для менеджера и агента.
Модель общая, но каждый слот занимает дополнительную память для KV и renderer.
Один слот хранит одно текущее продолжение. Чередование диалогов с одинаковой базой
может вызвать `replay`, сохраняя преимущество обработанной базы.
Параллельные HTTP-запросы выполняются последовательно под общим lock.
При превышении числа слотов вытесняется давно не использовавшийся.
Изменение sampling-параметров или эффективного лимита ответа создаёт другой слот.

## Изображения / read_pic

Поддерживается формат инструмента `read_pic.sh`: блоки `text` и `image_url`
с `data:image/png;base64,...` или `data:image/jpeg;base64,...` в сообщении `user`.
Настройки клиента менять не нужно. Изображение передаётся native API как
`{"type": "image", "blob": "..."}` вместе с текстом задания и предыдущей историей.
Допускается несколько блоков изображений в сообщении, в пределах возможностей модели.
Лимит одной картинки — 20 MiB, всего HTTP-запроса с историей — 64 MiB.
Внешние URL и пути файлов сервер не загружает; `read_pic` уже присылает сами байты.

Для изображения используется **Conversation**, поскольку Python Session API
принимает только текст и не выполняет обработку vision. Первый запрос с картинкой
восстанавливает полную переданную историю в мультимодальном контексте:
`mode=vision-rebuild`. Перенести checkpoint текстовой Session в Conversation
через используемый API нельзя, поэтому в этот момент обработка системного промпта
повторяется. При следующих репликах того же диалога — включая обычные текстовые
уточнения — используется сохранённая Conversation: `mode=vision-resume`.
Клиент должен продолжать передавать полную историю, включая блок изображения.
Изменённая история, новый независимый запрос или смена картинки без продолжения
истории требуют `vision-rebuild`; старые визуальные данные не подмешиваются.

Мультимодальные контексты имеют **отдельный пул**: `--max-vision-contexts 1`
по умолчанию, дополнительно к двум текстовым слотам. Слот создаётся только при
запросе с картинкой и занимает дополнительную память KV. Его создание, вытеснение
или ошибка не удаляют прогретые текстовые базы. После сброса диалога к чисто
текстовому запросу снова используется прежний текстовый checkpoint.

Модель должна содержать vision encoder. Сервер явно включает его на CPU по умолчанию:
Python API LiteRT с `vision_backend=None` вообще не создаёт vision executor,
в отличие от CLI, который сам разрешает backend до создания движка.
Можно явно задать `"vision_backend": "cpu"` (или `"gpu"`) в настройках модели.
Для модели без vision encoder установи `"vision_backend": "none"`, чтобы запускать
её только для текста. Для твоей мультимодальной Gemma прежний конфиг менять не нужно.
При старте `ENGINE_READY` показывает выбранный `vision_backend`.
Для мультимодального запроса в лог выводится `ttft_seconds` — время до первого
текстового фрагмента, включая обработку картинки, prefill и первый decode.
`prefill_seconds=unknown`: публичный потоковый API не позволяет отдельно измерить
эту фазу. Счётчики `usage` учитывают позицию native KV, включая визуальные токены.

## Запуск в Windows / PowerShell

Если репозитория на этом компьютере ещё нет:

```powershell
git clone https://github.com/vladisUl/cat-agent.git E:\radxa\gemma\cat-agent
```

Если уже есть — перейди в свой каталог cat-agent и выполни `git pull --ff-only`.
Останови штатный `litert-lm serve`, чтобы освободить порт 9379.
Из корня репозитория:

```powershell
cd E:\radxa\gemma\cat-agent
$py = "E:\radxa\gemma\litert-lm-venv\Scripts\python.exe"
& $py -m pip show litert-lm
& $py -m litert_server --host 0.0.0.0 --port 9379 `
  --config "E:\radxa\gemma\server-config.json"
```

Прежний `server-config.json` с `backend`, `cpu_thread_count`,
`speculative_decoding`, `max_num_tokens` подходит без изменений.
Имя `gemma4-12b` разрешается через тот же реестр, что использует CLI:
`%USERPROFILE%\.litert-lm\models\gemma4-12b\model.litertlm`.
Учитывается переменная `LITERT_LM_DIR`.

В конфигурации также можно явно указать `model_path` к файлу `.litertlm`.
Относительный путь считается от каталога JSON. При нескольких записях `models`
нужен `--model gemma4-12b`: один процесс обслуживает одну выбранную модель.

Сервер готов после `ENGINE_READY` и `SERVER_READY`.
Первый запрос для новой базы выводит `BASE_WARM_BEGIN` / `BASE_WARM_READY`;
следующие запросы с теми же настройками не должны повторять эти строки.
Адрес API остаётся `http://IP-компьютера:9379/v1`, имя модели — `gemma4-12b`.
Сервер предназначен для доверенной локальной сети; авторизации в нём нет.

## Linux

```bash
cd /opt/cat-agent
git pull --ff-only
/opt/litert-lm-venv/bin/python3 -m litert_server \
  --host 0.0.0.0 --port 9379 --config /path/to/server-config.json
```

При завершении через Ctrl+C сервер ждёт окончания активного вычисления, затем
закрывает контексты и движок. Если клиент оборвал поток, native decode дочитывается
до конца перед освобождением контекста: C callback не остаётся с удалённой Session.

## Проверка на реальной модели

В другом PowerShell из корня репозитория:

```powershell
$py = "E:\radxa\gemma\litert-lm-venv\Scripts\python.exe"
& $py -m litert_server.check_cache --model gemma4-12b
```

Для измерения на своём длинном системном промпте добавь
`--system-file "E:\путь\prompt_manager.txt"` (UTF-8).
Проверка отправляет три запроса: первый, повторный независимый и продолжение.
На только что запущенном сервере ожидаются `cold → base → resume`.
Если короткий тестовый лимит 64 токена оборвал ответ, третьим будет `replay`;
база всё равно останется в кэше.

Смотри `cached`, `evaluated` и `prefill_seconds` в логе.
У второго запроса `cached > 0`, а `evaluated` не включает системный промпт.
Не сравнивай только полное время ответа: генерация остаётся отдельной затратой.
`prefill_seconds` включает создание/прогрев слота на первом запросе и рендеринг
шаблона; это измерение сервера, не чистое время матричных операций.

## API и ограничения

- `GET /health`, `GET /v1/models`, `POST /v1/chat/completions`.
- Обычный JSON и SSE (`stream: true`), UTF-8.
- `max_tokens` и `max_completion_tokens` поддерживаются; конфликт значений — 400.
  Лимит ответа ограничивается сверху `max_num_tokens - 1`, фактический остаток
  контекста может быть меньше. История автоматически не обрезается.
- `temperature`, `top_p`, `top_k`, `seed`; `n=1`.
- В `usage` возвращаются `prompt_tokens`, `completion_tokens`, `total_tokens`,
  `prompt_tokens_details.cached_tokens`. В SSE статистика также есть в последнем
  chunk без необходимости менять клиент cat-agent.
- Роли: начальный `system`, `user`, `assistant`; последний — `user`.
  Текст и блоки `type=text`, `type=image_url` (PNG/JPEG в user). Звук, native tool calls,
  `response_format`, `stop` и reasoning не реализованы и отклоняются, а не игнорируются.
  Текстовые команды собственного протокола cat-agent передаются как обычный текст.
- Thinking отключён в шаблоне; допустим `reasoning_effort: "none"`.
- При ошибке inference слот удаляется. После ответа, оборванного лимитом токенов,
  следующий запрос восстанавливает явную историю от базы: неполный конец реплики
  не используется для прямого продолжения.
- `cache` (`disk` / `memory` / `no`) относится к настройке движка. Управление
  резидентными checkpoint выполняет этот сервер отдельно.
- Для надёжного возврата к базе отключён ring buffer локального attention.
  Это может увеличить расход RAM относительно штатного `serve`.

Три обращения к C API (рендер базы, сохранение и восстановление checkpoint)
изолированы в `runtime.py`. Сигнатуры проверены по тегам upstream 0.16.0/0.16.1/0.18.0.
Другие версии намеренно отклоняются до загрузки native-библиотеки: нельзя
угадывать ABI вызова через ctypes. Пакет автоматически не обновляется.

## Автотесты

Из корня репозитория; LiteRT-LM и модель для этих тестов не нужны:

```powershell
python -m unittest discover -s litert_server/tests -v
```

Тесты проверяют повторное использование базы, продолжение и редактирование истории,
чередование диалогов, LRU, параметры, ошибки, сериализацию, обрыв соединения,
реальный HTTP/SSE, передачу изображений, сохранение визуального диалога, независимость
пулов и адаптеры на подменённой границе native API.
Они не заменяют проверку native vision/inference, MTP, скорости и памяти на твоей модели.
